Speculative decoding: many tokens for the price of one

A field guide · fast LLM inference · June 2026

When a large language model writes you a paragraph, it does almost nothing useful most of the time. Generating each token means reading every weight in the model out of memory — tens or hundreds of gigabytes — to produce a single word, and the GPU's arithmetic units sit nearly idle waiting for that memory. Speculative decoding is a beautiful trick that turns this waste into speed: a small, cheap draft model guesses the next several tokens, and the big target model checks all of them in one forward pass. Most guesses are right, so you get several tokens per expensive pass instead of one — commonly a 2–3× speedup, and provably without changing a single thing about what the big model would have written.

Start with a counterintuitive fact: when a large language model generates text, it is bottlenecked not by how fast it can compute, but by how fast it can read its own weights from memory. Producing one token requires a full forward pass — every weight matrix loaded from high-bandwidth memory into the chip and multiplied once. At batch size one, those matrices are used for a single token's worth of math and then thrown away, so the GPU's thousands of arithmetic units finish almost instantly and then sit waiting for the next slab of weights to arrive. The expensive silicon is idle; the memory bus is the wall.

This is the crack speculative decoding pries open. Here is the key observation: because a forward pass is dominated by loading the weights, running it on five tokens in parallel costs almost exactly the same wall-clock time as running it on one. The weights are read once either way; checking five positions at once is nearly free extra arithmetic on units that were idle anyway. So if you could somehow know the next five tokens in advance, you could confirm them all in a single pass and emit five tokens for the price of one.

You can't know them — but you can cheaply guess them with a small model, and then check the guesses. That's the entire idea, and the rest of this piece is about making it precise: why parallel verification is free, how the accept-or-reject rule keeps the output identical to the big model's, exactly how much faster it goes, and the family of clever variants — Medusa, EAGLE, tree verification, lookahead — that push the trick further. 1. Why one token at a time is slow

To see why the trick works, you have to feel the bottleneck. A modern GPU can do hundreds of teraflops of arithmetic, but it can only move a few terabytes per second of data between memory and the compute cores. For a big model at batch size one, decoding a token touches every parameter exactly once and does only a couple of floating-point operations per parameter. The ratio of arithmetic to memory traffic — the arithmetic intensity — is tiny, far below the point where the compute units could be the limiter. The pass finishes the instant the weights arrive.

The consequence is the lever speculative decoding pulls: a forward pass that scores many token positions at once is barely more expensive than one that scores a single position, right up until you've put enough work in flight to saturate the compute units. Below that knee, extra parallel tokens are nearly free. The memory wall — parallel tokens are nearly free

A forward pass first pays a big fixed cost to load the weights, then a tiny cost per token. Slide the number of tokens scored in one pass and watch per-pass latency stay nearly flat (memory-bound) until compute finally becomes the limit.

Why batching doesn't already solve this. Serving many users at once does fill the GPU — that's why throughput-oriented servers batch requests. But it doesn't help the latency of a single response: your one conversation still emits one token per pass. Speculative decoding attacks exactly that single-stream latency, which is what a person waiting for an answer actually feels.

2. Guess, then check

Speculative decoding uses two models that share a vocabulary: a large target model $p$ — the one whose output you actually want — and a small, fast draft model $q$, maybe ten or twenty times cheaper to run. One step of the algorithm goes like this:

  1. Draft. Run the small model autoregressively to propose $\gamma$ candidate tokens $x_1, x_2, \ldots, x_\gamma$. This is cheap and sequential, but each step is fast.
  2. Verify. Run the big model once, in parallel, over the prompt plus all $\gamma$ proposals. A single pass yields the target's probability distribution at every one of those positions — $p(\cdot \mid \text{prefix})$ for each.
  3. Accept or reject. Walk left to right. Accept each proposed token according to a rule (next section) that compares $p$ and $q$. Stop at the first rejection; keep the accepted prefix.
  4. Correct and bonus. At the rejection point, sample one corrected token from an adjusted distribution. If all $\gamma$ were accepted, the same parallel pass already gives you one free bonus token at the end. Either way you advance, and repeat.

So each expensive pass of the big model yields anywhere from one token (everything rejected) to $\gamma + 1$ tokens (all accepted, plus the bonus). The draft model's job is simply to be right often enough that the average is comfortably above one. Put the two side by side and the payoff is obvious. Both lanes below generate the same sentence, and both are charged the same way — by the number of expensive big-model passes. 4. The lossless guarantee

Here is the part that makes speculative decoding a free lunch rather than a quality tradeoff. The accept/reject rule is built so that the token you finally emit is distributed exactly as if you had sampled from the big model $p$ directly. Not approximately — identically. The draft model only affects speed, never the output distribution.

The rule is a form of rejection sampling. Suppose the draft proposed token $x$, which it drew with probability $q(x)$, and the target assigns it probability $p(x)$. Then:

$$ \text{accept } x \text{ with probability } \min\!\left(1,\ \frac{p(x)}{q(x)}\right). $$

If the target likes $x$ at least as much as the draft did ($p(x) \ge q(x)$), accept it outright. If the target likes it less, accept it only proportionally. When a token is rejected, don't just resample from $p$ — that would double-count the mass you already tried. Instead sample the replacement from the residual distribution, the part of $p$ the draft under-proposed:

$$ p'(x) \;=\; \norm\big(\max(0,\ p(x) - q(x))\big) \;=\; \frac{\max(0,\ p(x) - q(x))}{\sum_{x'} \max(0,\ p(x') - q(x'))}. $$

Why does this reproduce $p$ exactly? Look at the total probability of emitting some token $x$ at this position. It's accepted with probability $\min(q(x), p(x))$ (the draft proposes it $q(x)$ of the time and keeps it with probability $\min(1, p/q)$), and it can also arrive via a rejection-and-resample, which contributes exactly $\max(0, p(x) - q(x))$. Add them:

$$ \min\big(q(x), p(x)\big) \;+\; \max\big(0,\ p(x) - q(x)\big) \;=\; p(x). $$

That identity is the whole proof — it holds term by term, whether $p(x)$ is bigger or smaller than $q(x)$ — and it's why the method is provably lossless. The greedy special case. If you're decoding greedily (temperature 0), the rule collapses to something intuitive: accept the draft token if and only if it matches the target's own $\argmax$ at that position. Verification becomes "did the small model pick the same word the big model would have?" — and the corrected token is just the big model's top choice.

5. How much faster?

The speedup hinges on one number: the average per-token acceptance rate $\alpha$ — how often the target accepts a drafted token. Model the accepted run as a geometric process: each proposal is accepted with probability $\alpha$, independently, until the first rejection. If you draft $\gamma$ tokens per step, the expected number of tokens you emit per step (including the one corrected or bonus token) works out to a tidy closed form:

$$ \mathbb{E}[\text{tokens per step}] \;=\; \frac{1 - \alpha^{\,\gamma+1}}{1 - \alpha}. $$

With $\alpha = 0.8$ and $\gamma = 4$, that's about $3.4$ tokens per expensive pass. But there's a catch: drafting isn't free. If one draft step costs a fraction $c$ of a target step, then a full speculative step costs roughly $\gamma c + 1$ target-equivalents (draft $\gamma$ times, verify once). Dividing the tokens gained by the cost gives the wall-clock speedup over standard decoding:

$$ \text{speedup} \;=\; \frac{1 - \alpha^{\,\gamma+1}}{(1 - \alpha)\,(\gamma c + 1)}. $$

This formula has real personality. Push $\gamma$ too high and you draft tokens that will be rejected anyway, paying $c$ for each wasted guess — there's an optimal draft length that grows with $\alpha$ and shrinks as the draft gets pricier. 6. The family of methods

The basic recipe needs a separate small model that shares your tokenizer — not always available, and an extra model to host. So most of the research since has been about where the draft comes from and how many guesses you verify at once.

Self-drafting: Medusa and friends

Why run a second model at all? Medusa bolts a few extra "heads" onto the target model itself — small layers that, from the current hidden state, predict the token two, three, and four positions ahead. The model drafts for itself, with almost no extra cost and nothing new to serve. Other self-speculative schemes use a subset of the target's own layers as the draft, skipping the rest until verification time.

Drafting in feature space: EAGLE

EAGLE sharpens the idea by drafting at the level of the model's hidden features rather than raw tokens: it autoregressively predicts the target's next feature vector, which is a smoother, more predictable signal than the discrete token. The result is markedly higher acceptance rates, and later versions add dynamically-shaped draft trees on top.

Don't guess one future — guess many: token trees

A single linear draft commits to one continuation. But you can instead propose a tree of candidate continuations — several possible next tokens, each branching into several after that — and verify the whole tree in one pass using a custom attention mask, so each node only attends to its own ancestors. The target then accepts the best root-to-leaf path. SpecInfer, Medusa, and EAGLE all use this token-tree verification: more candidates per pass means a longer expected accepted run, at the cost of scoring more positions (which, remember, is nearly free). Build a tree in the last widget and watch the expected accepted length grow.

No draft model at all: lookahead decoding

Lookahead decoding drops the draft model entirely. It runs the target in a Jacobi iteration that refines several future positions at once and harvests verified n-grams from its own recent outputs into a pool of guesses — a self-contained way to generate and check in parallel with no second network.

One ancestor worth naming. The whole lineage traces back to blockwise parallel decoding (2018), which first added auxiliary heads to predict several future tokens and verify them in one pass. Speculative sampling added the exact rejection rule that made it lossless for sampling, not just greedy decoding — and that's what turned a neat idea into a default.

7. What you actually get

In practice, speculative methods deliver wall-clock latency reductions without touching output quality at all (for the exact-sampling variants) — the only cost is hosting or training the draft mechanism. Rough numbers from the literature:

ApproachDraft sourceTypical speedupOutput
Speculative sampling separate small model ~2–3× exact — identical to the target
Medusa extra heads on the target ~2–3× exact, or relaxed "typical" acceptance
EAGLE / EAGLE-2 feature-level + draft tree ~3–4× exact — identical to the target
Lookahead none (self, Jacobi + n-grams) ~1.5–2× exact — identical to the target

Speedups are order-of-magnitude figures that vary widely with the model pair, the task (code and structured text accept more than free-form prose), batch size, and hardware. They are latency improvements at small batch; the advantage shrinks as batching already fills the GPU.

8. Why it works

Three facts have to line up for a free lunch this clean, and in language modeling they do.

The hardware leaves money on the table

Single-stream decoding is memory-bound, so the compute needed to verify several tokens at once is sitting unused. Speculative decoding spends that free compute on checking guesses. It is, in a sense, a way to convert idle FLOPs into reduced latency — which is only possible because the FLOPs were idle to begin with.

Most tokens are easy

Natural language and especially code are full of near-deterministic continuations — closing brackets, function names, common phrases, grammatical filler. A small model predicts these just fine, so the acceptance rate on the easy stretches is very high. The big model's judgment is only really needed at the genuinely uncertain forks — and those are exactly the tokens that get rejected and corrected, preserving quality where it matters.

Verification is cheaper than generation

Checking whether a sequence is right is one parallel pass; producing it from scratch is many sequential ones. Speculative decoding exploits this asymmetry — the same reason it's easier to verify a proof than to find one. The draft does the sequential guessing on the cheap model; the expensive model is reserved for the parallel, one-shot check.

9. What it means

Speculative decoding changed the economics of LLM serving without asking anyone to accept a worse model. Because the exact-sampling variants are provably lossless, there's almost no reason not to use one: you keep your model's behavior bit-for-bit and simply wait less. It's now standard in production inference stacks, and the draft mechanism — separate model, extra heads, or feature-level predictor — has become a normal part of how a fast model is shipped.

Open problems

  • Acceptance at scale. The gains depend on the draft being a good mimic of the target. Keeping acceptance high across domains, long contexts, and as models grow is an active target of methods like EAGLE.
  • Batching tension. Speculation spends spare compute, but a heavily batched server has little to spare. Making speculative decoding pay off under high concurrency — not just for a single latency-sensitive stream — is genuinely hard.
  • Training the drafter. The best self-drafting methods need the heads or feature-predictor trained against the specific target. Doing that cheaply, and keeping it in sync as the target is updated, is its own small engineering discipline.

The bottom line

Strip it down and speculative decoding is one idea: guessing is cheap, checking is parallel, and a parallel check costs almost nothing on hardware that was idle anyway. A small model does the sequential guessing; the big model does a single parallel verification; a one-line identity — $\min(p,q) + \max(0, p-q) = p$ — guarantees the answer is exactly what the big model would have said on its own. You don't get a different model. You get the same model, waiting for memory a lot less often.
