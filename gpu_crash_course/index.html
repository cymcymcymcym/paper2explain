A crash course & roadmap

Feed the Beast: a GPU crash course for AI researchers

For the ML researcher who wants to design better algorithms · no hardware background assumed · mental models · a roadmap · what to learn next, in what order, through what

You can train models for years and never need to know what a GPU is. But the moment you want to make something faster — fuse a kernel, understand why FlashAttention is "free," design an algorithm that actually flies — you hit a wall of words: warps, SMs, coalescing, occupancy, HBM. The good news: you do not need to become a hardware engineer. You need about five mental models, and one master idea — the GPU's math is cheap; its bottleneck is moving data. This post hands you those models, an interactive feel for each, and a concrete path forward. The goal is momentum.

Here is the situation you keep running into. You read that FlashAttention is "2–4× faster with the same FLOPs," and it sounds like a contradiction — how is doing the same arithmetic faster? You write a clean PyTorch model and it runs at 5% of the GPU's advertised TFLOPs, and you have no idea why. You hear that a kernel is "memory-bound" and nod along without knowing what would change if it weren't.

All of these have the same root, and it is not arcane. A GPU is a machine with an almost comical imbalance: it can do arithmetic far, far faster than it can fetch the numbers to do arithmetic on. Almost every performance story in modern ML is a story about that imbalance. Once you internalize it, "memory-bound," "fusion," and "FlashAttention" stop being jargon and become obvious.

So this is not a hardware course. We will not count transistors. We will build the handful of mental models that let an algorithm designer reason about a GPU — play with each one — and then lay out exactly what to learn next and in what order. Let's start with the one idea everything else hangs from.

1. A GPU is a throughput machine, not a fast machine

A CPU and a GPU are built around opposite philosophies. A CPU is a latency machine: a few very sophisticated cores, each engineered to finish one task as quickly as possible — deep pipelines, branch prediction, big caches, out-of-order execution, all spent to minimize the time to a single answer. Think of a sports car: one passenger, there in a flash.

A GPU is a throughput machine: thousands of simpler cores, none of them individually clever, collectively doing an enormous amount of the same work per second. Any single operation might take longer than on a CPU, but the total volume moved per second is staggering. Think of a fleet of buses: slow per trip, but enormous people-per-hour.

The crucial trick is how a GPU deals with waiting. When one group of threads stalls waiting for data from memory (which, as we'll see, is most of the time), the GPU doesn't sit idle — it instantly switches to another group of threads that has work ready. With enough work in flight, the waiting is hidden entirely behind useful computation. This is the whole game: a GPU is fast not because any part is fast, but because it is never idle — as long as you give it enough to chew on.

Latency vs. throughput

A batch of tasks runs on a few fast "CPU" lanes vs. many slow "GPU" lanes. The CPU finishes the first task sooner; the GPU finishes all of them sooner. Press run.

The first reframe. "Is my code fast?" is the wrong question for a GPU. The right question is "am I keeping it busy?" A GPU at 100% occupancy doing the wrong thing can still be slower than one at 40% doing the right thing — but a GPU you've left starving is the most common failure of all.

2. The hardware, just enough to be dangerous

You need a few nouns. Everything else can wait.

The SM (streaming multiprocessor). A GPU is a grid of these — an H100 has 132 of them. Each SM is a little independent worker with its own arithmetic units, its own register file, and its own slice of fast on-chip memory. When you launch work, the GPU sprays blocks of it across all the SMs. Your job, loosely, is to keep all of them fed.

The warp (32 threads in lockstep). Threads on a GPU do not act individually. They march in groups of 32 called a warp, and all 32 execute the same instruction at the same time, just on different data. This is the SIMT model — Single Instruction, Multiple Threads. It is why GPUs are so efficient at array math (everyone does c[i] = a[i] + b[i] together) and it has one sharp consequence: if threads in a warp need to take different branches of an if, the warp must execute both branches and mask off the threads that shouldn't run each one. Branch divergence is a real cost. Try it:

SIMT: a warp executes in lockstep

32 threads run the same instruction together. Add a data-dependent branch and watch the warp serialize — it runs both sides, masking threads, so divergence costs you.

The tensor core. Bolted onto each SM are specialized units that do one thing: small matrix-multiply-and-accumulate, very fast, in low precision (BF16/FP8). Essentially all the FLOPs in modern deep learning — every matmul in every attention and MLP layer — run on tensor cores. They are why an H100 quotes ~990 BF16 TFLOP/s: that number is a tensor-core number. The ordinary "CUDA cores" handle the rest (the elementwise glue, the softmaxes, the reductions), and those are usually where time quietly leaks away.

And how you actually launch work. You never address the 132 SMs by hand. You declare a grid of thread blocks; the GPU schedules each block onto some SM, where its threads — bundled into warps of 32 — share that SM's fast scratchpad and cooperate. Grid → blocks → warps → threads is the hierarchy you actually program. Choosing the block size is your first tuning knob: too small and there aren't enough warps resident to hide memory latency; too big and you run out of registers or shared memory and the SM can't hold enough blocks at once. Most of "tuning a kernel" is finding the block shape and tile size that keep both the math units and the memory system busy.

Think in warps, not threads. When you reason about a GPU kernel, the unit is the warp of 32. "How do 32 neighboring threads access memory together?" and "do they ever disagree on a branch?" are the two questions that decide whether a kernel is good or terrible.

3. The memory hierarchy — where the whole fight happens

Now the heart of it. The compute is fast; the problem is feeding it. A GPU has a steep hierarchy of memories, and the difference between the top and the bottom is enormous — not just in size, but in how fast and how far away each one is:

  • Registers — per-thread, instantaneous (~1 cycle), but tiny.
  • Shared memory / SRAM — per-SM scratchpad you control by hand, ~tens of cycles, ~up to 228 KB per SM.
  • L2 cache — shared across the chip, ~50 MB, automatic.
  • HBM (global memory) — the big pool, ~80 GB at ~3.35 TB/s, but hundreds of cycles away.

Read those last two lines together and the central tension jumps out. HBM bandwidth — 3.35 terabytes per second — sounds astronomical. But the compute is hungrier. An H100 can do ~990 trillion BF16 operations per second; to feed that at one byte per operation you'd need ~1000 TB/s, and you have ~3.35. The arithmetic units would starve, waiting hundreds of cycles for each trip to HBM. The fast memories (registers, SRAM) are ~10–100× quicker — but small. So the entire craft of GPU programming is: get data into fast memory and reuse it as much as possible before it has to go back. Feel the cliff:

The memory hierarchy

Click a level to see its size, bandwidth, and latency — and watch a single value's round-trip time. The drop from SRAM to HBM is the cliff every fast kernel is built to avoid.

Compute is free; memory is expensive. This inverts the instinct you brought from math and CPUs, where you count operations. On a GPU, a fused multiply-add is essentially free, and the byte you fetched to feed it is the expensive part. Count bytes moved, not FLOPs.

4. The compass: the roofline and arithmetic intensity

Everything above becomes one quantitative tool — the single most useful thing on this page for someone who wants to design algorithms. Watch the imbalance first, then we'll name it:

Feed the beast. When each byte from far-away HBM feeds only ~1 FLOP, the cores starve and utilization collapses (memory-bound). Load a tile into nearby SRAM and reuse each byte for many FLOPs, and the cores stay fed (compute-bound). The lever is reuse, not arithmetic.

Define a kernel's arithmetic intensity $I$ — how much math it does per byte it moves:

$$ I \;=\; \frac{\text{FLOPs performed}}{\text{bytes moved to/from HBM}} \quad \left[\frac{\text{FLOP}}{\text{byte}}\right]. $$

Now the performance you can actually achieve is whichever limit you hit first — the compute ceiling, or the bandwidth you can sustain times your intensity:

$$ \text{Performance} \;=\; \min\big(\,\underbrace{\pi}_{\text{peak FLOP/s}},\;\; \underbrace{I \times \beta}_{\text{intensity} \,\times\, \text{bandwidth}}\,\big). $$

Plot that and you get the roofline: a slanted line (memory-bound, rising with intensity) that bends into a flat line (compute-bound, capped at peak). The corner — the ridge point — sits at $I^\star = \pi/\beta$. For an H100 that's about $990 / 3.35 \approx \mathbf{295}$ FLOP/byte: you must do roughly 300 operations on every byte you fetch just to stop being memory-bound. A plain elementwise add does about 0.1. A big matmul does hundreds. That gap is the whole story of which ML ops are slow. Find your op on the roofline:

The roofline

Drag arithmetic intensity, or click a real op (add, softmax, attention, GEMM). Left of the ridge you're memory-bound — the fix is moving less data. Right of it you're compute-bound — the fix is more/faster FLOPs.

This is your compass. Before optimizing anything, ask: which side of the ridge am I on? Memory-bound (almost all of ML's elementwise ops, normalizations, and attention)? Then chasing FLOPs is pointless — cut data movement. Compute-bound (large matmuls)? Then feed the tensor cores better. The roofline tells you which lever to pull before you waste a day pulling the wrong one.

5. The four levers

Almost every GPU optimization you'll meet is one of four moves, and all four serve the roofline — either moving less data, or keeping the machine busy.

① Coalesced memory access

When the 32 threads of a warp read memory, the hardware serves them in fixed-size transactions. If the threads read contiguous addresses (thread $i$ reads element $i$), the whole warp is satisfied in one fat transaction — coalesced. If they read scattered or strided addresses, it can take up to 32 separate transactions for the same data. Same bytes, up to 32× the traffic. The fix is usually just laying out your data so neighboring threads touch neighboring memory.

② Tiling (use the scratchpad)

This is how you raise arithmetic intensity on purpose. Instead of streaming data from HBM for every operation, load a tile (a block) into shared memory once, then have the whole block of threads reuse it many times before moving on. The classic tiled matmul does exactly this: each tile loaded from HBM is reused across a whole strip of output, turning a memory-bound naïve loop into a compute-bound one.

③ Kernel fusion

Every separate GPU kernel reads its inputs from HBM and writes its outputs back. So a chain like y = relu(x @ w + b) done as three kernels makes the data round-trip to HBM three times. Fusing them into one kernel keeps the intermediates in registers/SRAM and touches HBM only once — at the start and end. For memory-bound ops, fusion is often a near-free 2–3× win. See the bytes vanish:

Kernel fusion: stop round-tripping to HBM

Run a chain of elementwise ops as separate kernels vs. one fused kernel. Each unfused stage pays a full read+write to HBM; fusion pays once. Watch the byte counter.

④ Occupancy

Remember that the GPU hides memory latency by switching to other ready warps. Occupancy is how many warps you have resident to switch among. Too few — because each thread hogs too many registers or too much shared memory — and there's nothing to switch to, so the latency stops being hidden. Enough occupancy is necessary to hide latency, though (a common trap) not sufficient for speed: a fully-occupied kernel still loses if it's thrashing HBM.

6. Worked example: why FlashAttention is "free"

Now the magic trick dissolves. Standard attention, for a sequence of length $N$, computes the scores $S = QK^\top$ (an $N\times N$ matrix), softmaxes it, and multiplies by $V$. The naïve implementation materializes that $N\times N$ matrix in HBM — writing $O(N^2)$ numbers out and reading them back to do the softmax and the second matmul. For long sequences that is a colossal amount of memory traffic, and the whole thing is brutally memory-bound. The FLOPs aren't the problem; the round-trips are.

FlashAttention changes the algorithm to respect the memory hierarchy. It never builds the full $N\times N$ matrix. It tiles $Q$, $K$, $V$ into blocks, loads a block into SRAM, computes that block's partial attention there, and accumulates the result using an online softmax — a running-normalizer trick that lets you finish the softmax incrementally without ever seeing the whole row at once. The scores live and die in SRAM; only the final output is written to HBM.

The payoff is exactly what the roofline predicts: identical FLOPs, a fraction of the HBM traffic ($O(N^2)$ → roughly $O(N)$ memory), and as a bonus the $N\times N$ matrix never has to fit in memory at all. That is the entire "2–4× faster with the same FLOPs" mystery — it was never about arithmetic. It was about not walking to HBM and back for a matrix you didn't need to store. Every one of the four levers is in there: tiling, fusion, coalesced blocks, and enough work to stay occupied.

This is the template for "a better algorithm." FlashAttention isn't a new mathematical result — it's the same attention, re-expressed so the data stays in fast memory. Most GPU-aware algorithm wins look like this: find the HBM round-trips, and design them away.

7. The roadmap — what to learn, in what order, through what

You now have the mental models. Here is how to turn them into skill, staged so each step pays off before the next. Resist the urge to start at the bottom with CUDA C++ and pointer arithmetic — for an ML researcher, the fastest momentum comes from writing a real kernel in Triton in an afternoon and seeing the roofline move.

StageGoalDo thisThrough
0 · Models The intuitions Internalize throughput, the memory hierarchy, the roofline (this post) you just did this
1 · First kernel Write GPU code that runs Vector add → fused softmax → tiled matmul, in Triton (Python-like, made for ML) Triton tutorials; Sasha Rush's GPU Puzzles
2 · Think in bytes Profile; find the bound Measure memory- vs compute-bound; read a profile; reason about HBM traffic Horace He, "Making Deep Learning Go Brrrr"; PyTorch profiler / Nsight
3 · Foundations Real parallel programming The execution model, shared memory, tiling, from the ground up; one CUDA matmul by hand PMPP (Kirk, Hwu & El Hajj); Simon Boehm, "How to Optimize a CUDA Matmul"
4 · ML systems Read & write real fused kernels FlashAttention; study production kernels; join the community FlashAttention (arXiv 2205.14135); GPU MODE lectures
5 · Frontier Squeeze the hardware Tensor-core programming, pipelining, warp specialization; then multi-GPU (NCCL, parallelism) CUTLASS / CuTe; vendor architecture guides

The order matters more than the speed. Each stage makes the next one legible: you can't appreciate CUTLASS until you've felt a tiled matmul, and you can't feel tiling until you've watched the roofline move on something you wrote yourself. Ship a Triton kernel before you open a textbook.

8. Insights to keep in your pocket

The mental models, compressed to the lines worth memorizing:

  • Compute is free; memory is expensive. Count bytes moved, not FLOPs.
  • The GPU is always waiting on memory. Performance is the art of hiding the wait — with reuse and with enough work in flight.
  • Think in warps of 32. Neighboring threads should read neighboring memory and agree on their branches.
  • Most ML ops are memory-bound. So fusion and tiling — not cleverer arithmetic — are usually the win.
  • Every HBM round-trip is a tax. Fuse to pay it once. FlashAttention is this idea taken seriously.
  • The roofline is your compass. Know which side of the ridge you're on before you optimize.
  • Occupancy is necessary, not sufficient. A busy GPU doing wasteful memory traffic is still slow.

The bottom line

You do not need to design hardware to design better algorithms on it. You need to think about data movement. The entire modern toolkit of efficient ML — fused kernels, FlashAttention, paged attention, quantization, all of it — is people who internalized a single sentence: keep the beast fed. The math is cheap; the bytes are dear; the art is reuse.

That's the glimpse and the path. The momentum comes from doing: open Triton this week, write a vector add, then a fused softmax, and profile it until you can say out loud whether it's memory-bound or compute-bound. The first time you watch a number you wrote move along the roofline, the rest of this roadmap will stop looking like a wall and start looking like a staircase.
